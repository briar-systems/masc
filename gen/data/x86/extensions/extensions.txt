# the x86 extension catalog, written by masc from the sources below
#
# a row is a feature a selection holds: an instruction set a CPUID bit enumerates, or an
# architectural state the psABI names. each row's own name is its spelling as mach's manifest spells
# the ones it has (sse41, sse42, cx16, pclmul, fsgsbase) and as XED spells the rest, in lower case,
# and any other spelling a consumer needs is an alias record naming the row. an ISA set of XED that
# is no row of its own, such as avx512bw_128 or apx_f_adx, is a requirement over rows, which the XED
# reader states (#29)
#
# the code width is execution state, not a row: the axis width of 16, 32 and 64 bits, which code
# switches (`.code16`, `.code32`, `.code64`), so a register or instruction that exists at one width
# requires its state value, as rax requires width=64. doitm, the data operand independent timing
# mode of IA32_UARCH_MISC_CTL (SDM Volume 1, 18.1), is the other axis, which the operating system
# sets and code does not switch. a flag an operating system sets to enable a feature is part of the feature's row
# (pku and ospku, klsupported and klenabled, a padlock unit and its enable bit), except where a
# source names the state itself: osxsave, osfxsr and sce, which the psABI lists. the ISA sets of
# XED that no CPUID bit enumerates and every x86 processor executes (i86 to i486, pentiumreal, ppro,
# pause and the nops) have no row, and their requirement is none
#
# an implication is stated only where a source states it, and the source is named at the row. the
# sources, all read at the revisions named:
#   Intel SDM 325462-093US (September 2026), Volume 1
#     10.5.1.2 sse: SSE instructions cannot be used unless CR4.OSFXSR is 1
#     13.2   osxsave: CR4.OSXSAVE can be set if and only if CPUID.01H:ECX.XSAVE is 1
#     13.3   avx, avx-512, mpx and amx: their instructions execute only with CR4.OSXSAVE 1, and amx
#            only in 64-bit mode
#     16.2   avx10: versions are inclusive, and every processor with AVX10 also has AVX, AVX2 and
#            AVX-512. Table 16-2 lists the AVX-512 families AVX10.1 includes. vaes, vpclmulqdq and
#            gfni stay enumerated by their own bits, so their EVEX forms need both the feature and
#            the version (avx10_1 does not imply them)
#     21.3   CPUID leaves: the bits the XED table below names
#     5.22   vmfunc: the instruction is invoked in VMX non-root operation, so it needs vmx
#   Intel Instruction Set Extensions and Future Features 319433-062 (June 2026)
#     1.4    Table 1-3: CPUID leaves 07H.01H, 1EH and 24H
#   Intel AVX10.2 Architecture Specification 361050-005US (June 2025)
#     3.1.2  avx10_vnni_int: a processor with AVX10_VNNI_INT also enumerates AVX10.2. AMX-AVX512 is
#            no longer sensitive to AVX10.2 (revision 4.0), so amx_avx512 implies amx_tile only and
#            an instruction of it also requires avx512f or an avx10 version
#   Intel APX Architecture Specification 355828-009US (August 2026)
#     3.1    apx_f is available only in 64-bit mode (3.1.4.2.1) and only with CR4.OSXSAVE 1 (Table
#            3.8). every processor with apx_f also enumerates apx_nci_ndd_nf, and one with both also
#            enumerates cmov (3.1.4.3.1), which is the catalog's one combination
#   x86-64 psABI e1ce098331da5dbd66e1ffc74162380bcc213236 (2025-03-12), low-level-sys-info.tex
#     Table "Micro-Architecture Levels": the baseline and the levels x86-64-v2 to x86-64-v4, which
#            are cumulative. the baseline has no level of its own in the psABI and none here
#   AMD64 Architecture Programmer's Manual Volume 3, 24594 revision 3.28 (September 2019)
#     D.2    Table D-1: the AMD instruction subsets and their CPUID flags
#   XED 0bcb6237345c5066726dcc08b3d87928df3b5b26 (2026-08-24), datafiles/**/cpuid*.txt
#     the CPUID names of every ISA set and which sets need more than one (fma needs avx, vaes needs
#            aes, sha512 needs avx). avx10_v1_aux is XED's CPUID.24H.01H:ECX[2] (avx10-2/cpuid.xed.txt),
#            the aux instructions of AVX10.2 on an AVX10.1 processor, so it implies avx10_1 and not
#            avx10_2. clzero is XED's CLZERO set (amd/xed-amd-clzero.txt), whose CPUID bit
#            gen/data/x86/isa-sets.txt states from Linux's x86 headers
#   LLVM bd58c858ea9b5a41716cd8e09935904cf2470d7b, llvm/lib/TargetParser/X86TargetParser.cpp
#     the ImpliedFeatures chains where no Intel or AMD document states one: sse to sse4.2, avx and
#            avx2, avx-512 on avx512f and avx512bw, and the vector extensions on their widths
#
# the closures agree with LLVM's wherever LLVM has the feature, and with the macros clang defines for
# each feature it is given (__AVX2__ and the rest), except in five places, each for the source
# named. sha512 and sm4 imply avx, where LLVM implies avx2 (XED gives sha512 and avx, sm4 and avx).
# the amx and apx rows imply osxsave, which LLVM's table does not model, and that they exist only in
# 64-bit mode is their instructions' requirement of width=64, as no row implies a state value. avx implies
# osxsave and so xsave, which clang's driver also enables with avx. amx_avx512 implies amx_tile,
# where LLVM implies avx10_2 (the specification removed that sensitivity). apx_f is one row, where
# LLVM splits it into nine features that the CPUID leaves do not enumerate singly
#
# the levels are the psABI's, which it defines for 64-bit code, so each sets width=64, and x86-64-v3
# lists osxsave as the psABI does, with the xsave it brings
#
# lines, one record each, fields separated by blanks:
#   row <name> <revision> <implied>...
#     an extension, its id the count of rows before it, its revision `-` for none, then the atoms selecting it brings
#   axis <name> <value>...
#     an execution state axis and its values, in the order of the set's axes, which number on from the rows
#   level <name> <kind> <atom>...
#     a level of kind arch, profile, cpu or psabi, the extensions it selects and the state values, as `axis=value`, it sets
#   alias <key> <name>...
#     another key a consumer spells, naming the rows and levels after it
#   conflict <a> <b>
#     two atoms no selection may hold together, the lower first
#   combination <by> <when> <implied>
#     `by` brings the comma list `implied` while every atom of the comma list `when` is held
#
# an atom is a row's or a level's name, or a state value as `axis=value`. each row's handle is its name by gen's one rule
# (emit.ident), as `zext.h` is ZEXT_H and `3dnow` _3DNOW, and a state value's is the same of `axis=value`, as XLEN_32
